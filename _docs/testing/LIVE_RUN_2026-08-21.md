## Data-state finding, worth knowing before reading any TDS number

The dev database holds **zero `TDSRecord` rows** despite five payment
requests carrying ₹15,900 of TDS between them. `TDSRecord` is created in
`payments/serializers.py:187`, inside `create()` — so the seeded demo
payments, which were written directly rather than through the API, never got
records. Two consequences: (1) TC-PAY-03/04's void-and-restore behaviour
cannot be exercised against the existing seed data, only against freshly

the TC-PAY-07 mechanism independently — the Payment Audit report's total
cannot be reading `TDSRecord` at all, since there are none, so it must be
summing `tdsAmount` off the payment requests exactly as the defect describes.

## Courier

- **TC-CUR-05 — the test document's stated expectation is WRONG. Measured in
  both directions.**

  The doc says: *"Dispatch, then change the REP's address → the dispatched
  shipment keeps the address it was sent to. Snapshots are frozen at
  dispatch. Correct by design."* **Snapshots are not frozen at dispatch.**

  Measured on CR-2026-0007:
  1. Dispatched, `snapAddress = "Office 12, City Mall"`.
  2. Changed the REP's live courier address → dispatched shipment's
     `snapAddress` became **"CHANGED ADDRESS AFTER DISPATCH"**, `snapPinCode`
     **999999**. The record of where the parcel was sent moved retroactively.
  3. Restored the address, then moved the shipment to **Delivered**.
  4. Changed the REP address a second time → `snapAddress` stayed
     **"Office 12, City Mall"**. Frozen.

  Mechanism, deliberate and commented: `courier/serializers.py:69-75`
  `to_representation` calls `refresh_snapshot()` for any shipment whose status
  is **not** in `TERMINAL_STATUSES`, so the address re-reads live in-flight;
  `courier/models.py:47` defines terminal as `{Delivered, Returned, Lost}`.
  The comment states the intent plainly: live-refresh in-flight "so REP/Trial
  address corrections reach it", frozen once terminal. `courier/views.py:147`
  also re-snapshots at every transition.

  So the freeze point is **delivery, not dispatch**. That is a defensible
  design (a typo corrected while the parcel is still moving should reach it),
  but it is not what the case asserts, and the difference is material: between
  dispatch and delivery, the shipment's address is not a record of what was
  sent — it tracks whatever the REP record currently says.

  This is the same mechanism behind the standing orphan warning (in-flight
  shipments re-read the address live), now measured rather than asserted.
  **Whether dispatch should freeze is a product decision, not a code
  question** — flagging rather than changing it.

  Correction note: I first wrote this case up as PASSING before running step
  2. It does not pass. The premature verdict is left visible here rather than
  quietly edited out, because it is the same failure mode this campaign keeps
  catching in the documents it inherited.

### TC-CFG-02 — PARTIAL, salvaged from a dead agent's leftover data

Not a completed case, but the mechanism is now measured. Work order 6
(`WO-DEMO-PR`) carries `projectRef: 'TCCFG-IKF Renamed'` — a value only a
rename test could have produced — while its `updatedAt` is still
**2026-06-23T22:38:54**, months old.

`project_ref` is a stored `CharField` (`workorders/models.py:26`) mapped 1:1
by the serializer (`workorders/serializers.py:39-40`), so this is not a live
lookup. The value changed without the timestamp moving, which means a bulk
queryset write. Confirmed: `config/views.py:30` —
`WorkOrder.objects.filter(project_ref=old_value).update(project_ref=new_value)`.

Three consequences:
1. **The rename does propagate to work orders.** TC-CFG-02's core behaviour
   works.
2. **It leaves no trace.** Queryset `.update()` bypasses `save()`, so
   `auto_now` never fires and `updatedAt` still reads June. Nothing records
   that the row changed or who changed it — the same blind spot as TC-USR-04.
3. **It is an exact-string match.** Any row whose `project_ref` differs by
   whitespace or case is silently skipped, and rows created after the rename
   with the old name are never caught. This is precisely the doc's caveat
   ("a rename by any other route leaves the copies behind"), and it is a
   direct consequence of the free-text-instead-of-FK problem in
   `.ai/schema-integrity.md`.

Still unverified: whether the rename reaches trials and the town master list.

**The two timestamps confirm the mechanism cleanly.** Config row 3 (the
renamed project name itself) has `createdAt 2026-06-23`, `updatedAt
2026-08-21` — it went through `save()`, so the timestamp moved. Work order 6,
rewritten by the same operation, still reads `updatedAt 2026-06-23`. Same
rename, one row records it, the other does not. That is the `.update()`

## NEW DEFECT — a bounced payment routed back through Draft loses its TDS
## permanently. Found by accident; statutory consequence.

Discovered while cleaning up: TDS record 3 sits `voided=True` while its
payment request (PR 7) reads **Payment Done**. A paid payment whose TDS
deduction is invisible to every total.

**The gap, in the code:**
- Void fires whenever a payment enters Bounced —
  `payments/serializers.py:222`: `new_status == 'Payment Bounced' and
  old_status != 'Payment Bounced'` → `TDSRecord...update(voided=True)` (:253).
- Un-void fires **only** on the direct return path —
  `:257`: `old_status == 'Payment Bounced' and new_status in ('Payment Done',
  'Sent to Accounts')` → `update(voided=False)` (:302).

So **any other exit from Bounced leaves the record voided forever.**
Bounced → Draft → Payment Done is the obvious one, and the UI's status
dropdown offers all four statuses freely with no restriction on order — a
user correcting a mis-marked bounce by first parking it back in Draft
silently destroys the TDS record's validity.

**Reproduced unintentionally, which is the point** — this was not a
contrived sequence, it is what I did while testing something else:
PR 7 Draft → (PATCH) Payment Bounced → (PATCH) Draft → (UI) Payment Done.
End state: `status: Payment Done`, `tdsAmount: 1000.00`, TDS record
`voided: True`. The ₹1,000 is owed to the tax authority and appears in no
total.

**It hides itself.** `GET /api/tds/` excludes voided records, so an earlier
read in this same session returned `{"tdsRecords":[],"total":0}` while
record 3 existed all along. Nothing in the UI or the API surfaces a voided
record attached to a paid payment. The only way I found it was counting rows
in the shell.

**Why this outranks most of the case list:** TDS is a statutory filing
obligation. Under-reporting is not a cosmetic bug. And the existing 143
payments tests all pass — `test_08` covers the un-bounce restore on the
direct path only. As with the payment save bug and TC-PAY-06, **the untested
branch is the broken one.**

Suggested fix, not applied: un-void whenever a payment leaves Bounced for any
non-bounced status, or block the Bounced → Draft transition outright. Which
one is a product decision.

## TC-CFG-02 — COMPLETE, and the doc's caveat is now a measured mechanism

**There are two rename paths and only one of them cascades.**

- `POST /api/config/rename/` (`config/views.py:121`) — renames the row AND
  runs `RENAME_CASCADES` (`:86-91`). For `project_name` that is
  `cascade_project_rename` (`:28-31`): `Trial.trial_type`,
  `TrialCityLocation.trial_type`, `WorkOrder.project_ref`.
- `PUT /api/config/<id>/` — the plain ModelViewSet update. Renames the
  ConfigOption row **only**. Every denormalized copy is left holding the old
  string.

Measured both ways. A plain PUT setting config 3 back to "IKF Trials"
returned 200 while trial 17 and work order 6 still read the old value. The
proper endpoint then reported `{"trials": 2, "trialCities": 1,
"workOrders": 1}` and all three followed.

This is exactly the doc's warning — *"Only through this screen. A rename by
any other route leaves the copies behind."* — now with the mechanism named.
Any script, admin action, or future endpoint that writes a ConfigOption
directly silently orphans every copy. The comment at `config/views.py:20-24`
is explicit that this function exists only because those tables store their
own copy of the string, and notes `CSRProject` is exempt **because it uses a
ForeignKey** — the one table that got the schema right needs no cascade.
Direct evidence for the FK argument in `.ai/schema-integrity.md`.

**Resolves the "unrecoverable" open item.** The cascade covers
`Trial.trial_type`, and trial 17's type had been "IKF Trials" before the dead
agent's rename — so config 3's original value was recoverable after all.
Repaired: config 3, trial 17, trial cities and work order 6 all read
"IKF Trials" again. Nothing left outstanding from the failed agent round.

### NEW DEFECT — a cancelled TDS can be marked deposited to the tax authority

**TC-PAY-08 half-passes.** Marking Aug 2026 deposited worked — status
`Deposited`, `depositedDate` set. But it reported `updated: 3` while the
