## 1. P0 — Permission cluster (the Sanket / access bugs)

### Root-cause summary

The RBAC model treats modules as independent islands; the screens do not. Backend
`ModulePermission` (`backend/permissions/enforcement.py:40-57`) denies any request for a
module the user has no grant row on. The grant grid saves the FULL grid state and
`apply_grants` (`backend/permissions/views.py:17-56`, delete at :35) removes every module
left unticked. So a user granted "Vendors + Work Orders" has **no `config` row**, and:

- On login, `refreshAllFromAPI()` (`src/utils/adminStorage.js:212-224`) fires 8
  `configAPI.getByCategory()` calls, all gated by the `config` grant
  (`backend/config/views.py:31-32`) → all 403.
- `fetchCategory` (`adminStorage.js:72-86`) swallows the error and falls back to defaults —
  and the defaults for `vendorTypes`, `entityTypes`, `vendorNames`, `courierItems` are
  **empty arrays**.
- Every dropdown fed by those caches renders blank: `VendorModal.jsx:110-111`
  (service type, entity type), WO project/vendor pickers, courier items.

This single mechanism explains the client's exact words: "Service types ka option nahi
hai", "All entities", "still can't view added vendors" (the vendor-name picker is
config-fed via `getFilteredVendorNames`).

Symptom → cause map:

| Client report | Root cause | Fix |
|---|---|---|
| Service types / entities dropdowns empty | missing `config` grant → 403 → empty fallback | F1 |
| "Can't view added vendors" despite vendor grant | config-fed vendor-name picker + possibly wiped grant row | F1 + F5 |
| No Raise Payment despite WO access | `WorkOrderCard.jsx:166` requires `canEdit('payments')` | F4 (decision) + F3 |
| "Extra access auto-given to some users" | `backfill_permissions` seeded ADMIN = view+edit on ALL modules | F6 |
| Grants UI still says "Social Media" | label lives in backend `registry.py:43`, FE already renamed | F2 |

### F1 — Ungate config READS (root fix for all blank dropdowns)

**GOAL:** any authenticated user can read config reference data (dropdown labels), so no
module screen ever renders blank dropdowns because of a missing `config` grant. Writes
stay locked.

**Evidence:** `backend/config/views.py:31-32` gates the whole viewset
(`permission_classes = [IsAuthenticated, ModulePermission]`, `permission_module = 'config'`).
Reference data is non-sensitive (project names, seasons, vendor types, bank names, courier
items). Precedent: the per-report read endpoints were created for exactly this class of
problem (report screens needed reads without operational grants — issue #2 on the client
sheet, already shipped).

**Change (backend only):**
- In `backend/config/views.py`, replace the blanket `ModulePermission` with a small
  read-open/write-gated permission. Follow the existing style of `enforcement.py`:

  ```python
  class ConfigReadOpen(ModulePermission):
      """Config reference data is readable by any authenticated user; writes
      still require the 'config' grant."""
      def has_permission(self, request, view):
          if request.method in ('GET', 'HEAD', 'OPTIONS'):
              return bool(request.user and request.user.is_authenticated)
          return super().has_permission(request, view)
  ```
  Put it in `backend/permissions/enforcement.py` (generic: e.g. `ReadOpenModulePermission`)
  or locally in `config/views.py` — prefer `enforcement.py` so intent is documented at the
  security boundary. Keep `permission_module = 'config'` for the write path.
- Check every function view in `config/views.py` (there is at least one `@api_view` around
  :141) for the same treatment.

**Files:** `backend/permissions/enforcement.py`, `backend/config/views.py`. No migration.

**Tests:** add to `backend/config/tests.py` (or permissions tests): user with NO grants →
GET category = 200; POST/PUT/DELETE = 403; user with `config` can_edit → writes 200.

**Acceptance:** log in as a user granted only `vendors` — Add Vendor dialog shows service
types / entity types / bank names populated. No 403s for `/config/` GETs in the network log.

### F5 — Prod diagnostic: Sanket's grants + invisible vendors (sheet #16)

**GOAL:** confirm (not assume) why Sanket and the "old vendors invisible" user are broken,
before any further code. Distinguish "grant rows missing/wiped" from "config-dependency
blanks" (F1's territory).

**Evidence for the hypothesis:** `apply_grants` deletes any module unticked at save time
(`backend/permissions/views.py:35`) — a partial grid save produces exactly the reported
state. `GrantChangeLog` (same file) records every change with before/after, so the history
is queryable.

**Change:** none — this is a server-side lookup the USER runs (production access only).
Give him this, ready to paste (`mysql -u root auth_db` or Django shell via
`/root/TTA/backend/venv/bin/python manage.py shell`):

```sql
-- current grants for the affected users
SELECT u.email, p.module, p.can_view, p.can_edit
FROM permissions_usermodulepermission p JOIN accounts_user u ON u.id = p.user_id
WHERE u.email IN ('<sanket-email>', '<affected-user-email>')
ORDER BY u.email, p.module;

-- who changed their grants, and what got removed
SELECT actor_email, target_email, source, created_at, changes
FROM permissions_grantchangelog
WHERE target_email IN ('<sanket-email>', '<affected-user-email>')
ORDER BY created_at DESC LIMIT 10;
```

(Verify exact table names with `SHOW TABLES LIKE '%permission%'` first — Django default
naming assumed here.)

**Acceptance:** we can state per user: which grants exist, when config/vendors rows were
removed and by whom. Then: if grants are missing → re-grant via the UI (with F3 live); if
grants exist and vendors list is still empty → new investigation (queryset filters in

### F7 — DECISION + fix: bounced WO never reaches "Past Work Orders" (sheet #11)

**GOAL:** a fully-paid work order ends up in Past Work Orders even if it had bounced
payments in its history — via the flow the user chooses.

**Evidence:** `src/components/workorders/WorkOrderManagementPage.jsx:125-144` — three

and `pastWorkOrders` both require `bouncedPaymentCount === 0`. So Fully Paid + unresolved

BE `e19f429`, "moves bounced record to Past Payments", see comment at
`WorkOrderManagementPage.jsx:316-334`) zeroes the count → WO then classifies as past. The
designed path EXISTS; the literal ask ("move once fully paid") does not.

**Options:**
- **A (recommended): no code.** Once deployed, demo Resolve to the client: resolve the
  bounce → WO moves to Past. Matches the non-destructive Phase-1 design intent.
- **B:** reclassify `Fully Paid` WOs into `pastWorkOrders` even with
  `bouncedPaymentCount > 0` (drop the count check from the past filter, keep it in
  active). One-file FE change — but it hides unresolved bounces from the "Needs
  Resolution" surface; the count would need a badge on the past card instead. Riskier for
  bookkeeping honesty.

**Ask the user; default to A.**

### F9 — Config value rename does not cascade (volunteer → scout; sheet #13's sibling)

project-rename implementation first (`git show 1958952` in tta_backend) and copy its shape,
including how it distinguishes rename from delete+create — the FE saves categories via
delete+bulk (`adminStorage.js:96-104`), which may make renames LOOK like delete+create;
if so the cascade must hook the config update path the same way the project fix did, or the
FE save flow needs a true update call. **Investigate that commit before choosing.**
