## #17 totals — DECIDED (option B) and built

Owner chose **option B**: a bounced payment moved no money, so it contributes
to none of the three money columns. The totals row foots again.

**And the owner caught what option B would have broken.** The strip reported

Added `bouncedGross` to `computeTotals`, surfaced under the status line as

Tests updated — including replacing the earlier assertion that gross and net
stay as booked on bounced rows, which encoded the pre-decision behaviour.

## DECIDED ABOVE — original writeup kept for the reasoning

Raised by the review agent, verified: `PaymentAuditReport.jsx:746-748` renders
Gross, TDS and Net side by side in one totals row. The fix excludes bounced
payments from **TDS only**, so on a bounced row (gross 50000, tds 1000, net
49000) the totals read Gross 50000 · TDS 0 · Net 49000 — and
50000 − 0 ≠ 49000. The row visibly does not add up.

Three options:

**A. Leave it.** TDS is the statutory number and is now correct; the footing
is cosmetic. This is still strictly better than before, when the row footed
but the TDS figure was wrong — the defect reported four times.

**B. Exclude bounced from all three.** Most coherent semantically: a bounced
payment moved no money, so no gross left, no net arrived, no TDS was
deducted. The row foots again and the `bounced` count still shows how many
were excluded. **My recommendation** — but it changes two displayed numbers
beyond the reported defect, so it is the owner's call, not mine.

**C. Show bounced as a separate sub-total line.** Most informative, most work.

Not changed unilaterally: the complaint was specifically about TDS, and
altering Gross and Net is scope beyond it.

## #6 concurrent item loss — FIXED (main session). No migration needed.

Tracker row #6 (Nirja), "Package slip - item added separately was missing" —
the last data-loss defect on the sheet.

**Approach: optimistic locking, using the `updated_at` column that already
exists** (`courier/models.py:96`, `auto_now=True`). No migration.

The client echoes back the `updatedAt` it loaded; if the row has moved since,
the write is refused with **409** and a message that names the problem and the
remedy — *"changed by someone else while you were editing it. Reload to see
their changes, then redo yours — saving now would erase their work."*
Enforced only when the field is present, so older clients and scripts behave
exactly as before; they simply do not get the protection.

`_normalise_ts` compares by instant rather than by spelling. That is not
defensive padding — proven live: the serializer emits
`2026-08-21T05:50:22.296609Z` while the database holds `+00:00`. A raw string
comparison would have raised a false conflict on **every** save.

Wired frontend: `openEdit` records `loadedUpdatedAt` from the loaded shipment,
`saveShipment` sends it. Verified `updatedAt` is actually exposed by the
serializer (`courier/serializers.py:51`) — had it not been, the token would
have been empty and the lock would have silently never engaged.

**Verified live against the running server**, the exact three-step scenario:
B loads 6 items → A adds a 7th and saves (200) → B saves its stale list
(**409**), and A's item survived. Before the fix, step 3 deleted it.

5 backend regression tests + 1 frontend wiring test. Reverse-checked: with the
lock disabled, 2 fail including `test_THE_BUG_stale_save_is_refused_instead_of_erasing`.

One existing wiring test needed updating: it asserted the literal call shape of
`courierAPI.update(...)`, which adding a field broke. Its real guard — that the
NORMALIZED item array reaches the API, never the raw editing-shape one — is
unchanged and still passing.

**Suites: 266 frontend · 509 backend, all green.**

### Adversarial review found a HOLE in the N3 fix — confirmed and closed

A read-only review agent was pointed at every change made today. It reported
that N3, as first implemented, **bypassed both money guards**. I reproduced it
live before acting, and it was correct.

**The hole.** The first fix widened the exit-from-Bounced branch and un-voided
the TDS on *every* exit, but the two guards (`bounce_resolved`, retry-exists)
stayed nested under `if new_status in ('Payment Done','Sent to Accounts')`.
The only new transition the widening allows is **Bounced → Draft**, and that
route skipped the guards entirely while still running `update(voided=False)`.

Reproduced live: resolved a bounce, confirmed the direct un-bounce returns
**400** — *"already resolved and is frozen history"* — then PATCHed the same
record to **Draft**: **200**, and `voided` went `True → False`. A deduction for
money settled outside the system, reactivated through the side door, and
`mark_deposited` would then report it to the tax authority.

My own earlier verification missed this because I only tested Bounced → Draft
on a *clean* payment. That case worked; the guarded cases were never exercised.

**The fix.** Both guard conditions are now computed for every exit from
Bounced, as `handled_elsewhere`. On the paid path they still `raise` (the user
asked for money to move and must be told why it did not). On the Draft path
they do not raise — parking a bounce back in Draft moves no money and the UI
offers it — but the un-void is skipped.

Verified live, all three cases:
| case | expected | result |
|---|---|---|
| resolved bounce → Draft | stays voided | PASS |
| bounce with a retry → Draft | stays voided | PASS |
| clean bounce → Draft | un-voids | PASS |

The third matters as much as the first two: the fix must not over-correct and
re-break what N3 set out to fix.

Regression tests `test_14b` and `test_14c` added to
`payments/test_tds_flow_map.py`.

### Separate pre-existing bug found while writing those tests

`payments/serializers.py:79` called `u.username`. This project's User model
sets `USERNAME_FIELD = 'email'` (`accounts/models.py:74`) and **has no
`username` attribute**, so `get_bounceResolvedBy` raised `AttributeError` →
**500** on any read of a resolved payment request whose resolver had no
first/last name set.

`or` had been hiding it: every named user short-circuits before reaching the
bad attribute, so it only fires for a user created with an email and no name —
entirely plausible in production. Not introduced today; the new test just
happened to create a nameless user.

Fixed to `u.email`, matching `permissions/serializers.py:17,36`,
`otp/views.py:178` and `csr/views.py:246`, which all use email as the fallback.
`payments/serializers.py:79` was the only place in the codebase using
`.username`.
