How to run this

Work down a module in order. Each case names what to do, what should happen, and whether it is expected to work. A case marked known defect that passes is just as important to report as one marked should pass that fails.

Record only three things per case: pass, fail, or blocked. Where it fails, the note already says why — you do not need to diagnose it.

What this is not

It is not a specification. It describes the product as it stands on 21 August 2026, including behaviour nobody asked for and behaviour that was asked for and never built. Where a case traces to something your team reported, the date of that report is given.

Counts of boxes on each screen are counted from the screens themselves and include search and filter controls, not only data entry.

Before the first case

Where the app starts, and the road through it

One trial, from an empty system to a paid vendor and a report. Every operator passes through these ten steps in this order; nothing later works if an earlier step was skipped.

Who does what

In practice the work splits: project setup and oversight on one side, day-to-day operations — partners, courier, vendors, payments — on the other. The system does not enforce that split; module grants do. A user sees only the modules granted to them, so a tester should run each module as the role that actually uses it, not as super admin.

Where a trial can stall

A town with no partner assigned has no courier address and no venue, so steps 5 and 10 have nothing to show for it. That is not a fault — it is an incomplete setup, and it is what a blank on the Trials Report usually means. 45 of 100 town records currently have no ground address.
